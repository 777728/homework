## 二、问题描述与需求分析

### 2.1 问题描述

设计一个一元稀疏多项式的简单计算器，用带头结点的单链表存储多项式，
实现建立、输出、相加、相减、相乘、求导与求值；并在此基础上实现线性方程组的求解。

### 2.2 功能需求

| 编号 | 功能 | 输入 | 输出 | 难度 |
| :--: | ---- | ---- | ---- | :--: |
| F1 | 建立多项式 | 系数、指数序列或数学表达式 | 多项式链表 | A |
| F2 | 输出多项式 | 多项式 | 指数降序的数学表达式 | A |
| F3 | 相加 | A、B | A+B | B |
| F4 | 相减 | A、B | A−B | B |
| F5 | 相乘 | A、B | A×B | B |
| F6 | 求导 | A | A′ | B |
| F7 | 求值 | A、x₀ | A(x₀) | A |
| F8 | 解线性方程组 | 增广矩阵 | 解的情况 + 通解 | C |

### 2.3 非功能需求

- **正确性**：同类项必须合并，系数为 0 的项不得留在链表中；
- **健壮性**：非法输入（如 `3x^`、`abc`、非数字菜单项）不得使程序崩溃；
- **可维护性**：算法与界面分离，每个函数职责单一、有简短注释；
- **资源**：所有 `malloc` 的结点在程序结束前必须释放，不留内存泄漏；
- **易用性**：菜单清晰，操作有提示，结果可复用。

### 2.4 关键约束

一元**稀疏**多项式：项数远小于最高次数。例如 `9x^8+3x+7` 只有 3 项，
最高次数却是 8；实际应用中 `x^1000+1` 这种情况很常见。这一特征直接决定了
存储结构的选择——不能用「下标即指数」的数组。

## 三、CDIO 四阶段

### 3.1 C（Conceive）构思

**① 抽象数据类型设计**

先不考虑存储，只描述"多项式是什么、能做什么"：

```
ADT Polynomial {
数据对象：
    D = { aᵢ | aᵢ = (cᵢ, eᵢ), cᵢ ∈ R \ {0}, eᵢ ∈ N, i = 1..m, m ≥ 0 }
    每个数据元素表示多项式中的一项，cᵢ 为系数，eᵢ 为指数，且 eᵢ 互不相同
数据关系：
    R = { <aᵢ₋₁, aᵢ> | eᵢ₋₁ > eᵢ, i = 2..m }
    即所有项按指数严格递减排列

基本操作：
    CreatPolyn(&P, coef[], expn[], n)   由系数、指数序列建表
    DestroyPolyn(&P)                    销毁
    PrintPolyn(P)                       按指数降序输出
    AddPolyn(Pa, Pb, &Psum)             求和
    SubPolyn(Pa, Pb, &Psub)             求差
    MultiplyPolyn(Pa, Pb, &Pmul)        求积
    DerivPolyn(P, &Pd)                  求导
    EvalPolyn(P, x)                     求值
} ADT Polynomial
```

**② 存储结构选择**

| 方案 | 空间 | 加法时间 | 结论 |
| ---- | ---- | -------- | ---- |
| 数组，下标 = 指数 | maxexp+1 个单元，稀疏时浪费极大 | O(maxexp) | ✗ 不可行 |
| 数组，存 (系数,指数) 有序对 | 2m 个单元，但插入需移动 | O(m²) | △ 可行但不优 |
| **带头结点的单链表** | m 个结点，按需分配 | **O(m+n)** | ✓ 采用 |

**③ 模块划分（低耦合、高内聚）**

```
              ┌──────────────────────────────┐
              │       界面层（二选一）        │
              │  main.c   控制台菜单         │
              │  webui.c  表单窗口(图形界面) │
              └──────┬──────────────┬────────┘
                     │              │
   ┌─────────────────▼──┐   ┌───────▼─────────────┐
   │ ui.c/.h  界面工具  │   │ Polynomial.c/h      │  多项式 ADT
   └────────────────────┘   │ LinearSolver.c/h    │  方程组求解
                            └─────────────────────┘
```

`Polynomial.c` 不包含任何 `printf` 菜单代码（只有输出格式函数），
`ui.c` 不知道"多项式"是什么，`main.c` 与 `webui.c` 只负责把界面和算法串起来。
这样更换界面或更换存储结构时，另一部分无需改动——本项目实际做到了：
图形界面是在控制台版完成后追加的，算法模块一行未改。

### 3.2 D（Design）设计

**① 存储结构定义**

```c
/* 每一项对应一个结点 */
typedef struct LNode {
    double        coef;    /* 系数 */
    int           expn;    /* 指数 */
    struct LNode *next;    /* 后继指针 */
} LNode, *Link;

/* 多项式链表：带头结点，尾指针便于 O(1) 尾插 */
typedef struct {
    Link head;   /* 头结点（哨兵），head->next 才是第一项 */
    Link tail;   /* 尾结点，空表时 tail == head */
    int  len;    /* 项数（不含头结点） */
} LinkList;

typedef LinkList Polynomial;
```

设计要点：

1. **头结点**：使第一个位置也有前驱，插入/删除时不必特判空表与表头，
   所有删除操作统一写成 `prev->next = cur->next`；
2. **尾指针**：有序归并时结果总是追加到表尾，有 `tail` 才能做到 O(1)；
3. **len 字段**：求项数 O(1)，也便于调试时校验；
4. **不变式**：任何时刻链表都满足"指数严格递减、无零系数项"，
   后续所有算法都以此为前提，无需再排序。

**② 内存布局示意**

```
        head            ┌──────┐   ┌──────┐   ┌──────┐
     ┌────────┐         │ 9.0  │   │ 3.0  │   │ 7.0  │
     │ coef=0 │  next   │  8   │──▶│  1   │──▶│  0   │──▶ NULL
     │ expn=0 │────────▶└──────┘   └──────┘   └──────┘
     │ next ──┘            ↑                      ↑
     └────────┘         第一项                   tail
      （哨兵，不存数据）      表示 9x⁸ + 3x + 7
```

**③ 核心算法设计**

**算法 1：有序插入 + 合并同类项（InsertTerm）**

```
输入：多项式 P，系数 c，指数 e
1. 若 |c| < 1e-12，直接返回（零项不入表）
2. prev ← 头结点；cur ← 第一个结点
3. 当 cur ≠ NULL 且 cur.expn > e 时：prev ← cur；cur ← cur.next
4. 若 cur ≠ NULL 且 cur.expn == e：          // 同类项
       cur.coef ← cur.coef + c
       若 |cur.coef| < 1e-12：删除 cur        // 相加抵消
5. 否则：申请新结点 s，插入 prev 与 cur 之间
        若 cur == NULL，更新 tail ← s
```

时间复杂度 O(m)，一次遍历即可完成"查找位置 + 合并"。

**算法 2：多项式相加（有序归并）**

两个链表都已按指数降序排列，用双指针同步扫描：

```
a ← Pa 的第一项；b ← Pb 的第一项
当 a ≠ NULL 且 b ≠ NULL：
    若 a.expn > b.expn：把 a 追加到结果尾部；a ← a.next
    若 a.expn < b.expn：把 b 追加到结果尾部；b ← b.next
    否则：把 (a.coef + b.coef, a.expn) 追加到结果尾部；a、b 同时后移
把剩余的一段整体接到结果尾部
```

时间 **O(m+n)**，空间 O(m+n)（结果另建，不破坏 A、B 以便连续运算）。

**算法 3：多项式相减**

与加法完全相同，只是把 B 的每一项系数乘以 −1（参数 `signB`）。
**这一点是易错点**：不能让 B 的项原样接入结果，否则 `A−B` 会变成 `A+B`。

**算法 4：多项式相乘**

朴素做法是双重循环后统一排序，代价 O(mn·log(mn))。本程序利用有序性优化：

```
结果 R ← 空表
对 A 的每一项 aᵢ：
    临时表 T ← 空表
    对 B 的每一项 bⱼ：
        T 尾插 (aᵢ.coef × bⱼ.coef, aᵢ.expn + bⱼ.expn)
        // 固定 aᵢ 时，乘积指数随 bⱼ 递减，故 T 天然有序
    R ← R + T                       // 一次 O(|R|) 的有序归并
```

时间 O(m·(n+|R|))，无需额外排序，且直接复用加法代码。

**算法 5：求导**

逐项 `(c·x^e)' = c·e·x^(e-1)`，指数保持降序，用 `InsertTerm` 统一处理。
**易错点**：常数项（e=0）必须跳过，否则会产生指数为 −1 的非法项。

**算法 6：求值**

```
sum ← 0
对每一项 t：sum ← sum + t.coef × x^t.expn
```

其中 `x^e` 用快速幂（二进制拆分）计算，O(log e) 次乘法，
比调用 `pow()` 更快且无额外的精度损失。

**算法 7：高斯-约当消元（难度 C）**

```
row ← 0
对每一列 col = 0..n-1：
    在 row..m-1 中选出 |a[i][col]| 最大的行，与第 row 行交换   // 列主元，抑制误差
    若该列全为 0：跳过（该列对应自由变量），row 不前进
    归一化：第 row 行整体除以 a[row][col]
    消元：对所有 i ≠ row，a[i][j] -= a[i][col] × a[row][j]
    row ← row + 1
```

消元后矩阵为行最简形，可**直接读出**：

- r(A) = 主元个数；
- 无解 ⟺ 存在 `0 0 … 0 | 非零` 的矛盾行；
- 唯一解 ⟺ r(A) = n；
- 无穷多解 ⟺ r(A) = r(A|b) < n，自由变量 n − r(A) 个；
- 特解 = 自由变量取 0 时的主元值；
- 基础解系 = 依次令某个自由变量为 1、其余为 0，回代求主元变量。

时间复杂度 O(m·n²)，空间 O(mn)。

### 3.3 I（Implement）实现

**① 编码规范**

- 一个函数只做一件事，函数上方用 2~5 行注释说明"做什么、参数含义、易错点"；
- 统一返回状态码 `POLY_OK / POLY_ENOMEM / POLY_EINVAL / POLY_EPARSE`，
  调用者必须检查；
- 头文件只放声明，实现文件内部的辅助函数一律 `static`；
- 编译选项 `-std=c11 -Wall -Wextra`，要求**零警告**。

**② 关键实现片段**

*建立结点时"指针的指针"的用法*（对应题目要求"注意参数 p 的传递方式"）：

```c
int MakeNode(Link *p, double coef, int expn) {
    Link s = (Link)malloc(sizeof(LNode));
    if (s == NULL) { *p = NULL; return POLY_ENOMEM; }
    s->coef = coef; s->expn = expn; s->next = NULL;
    *p = s;                 /* 通过二级指针把新地址带回调用者 */
    return POLY_OK;
}
```

若参数写成 `Link p`（值传递），函数内的修改只作用于副本，
调用者的指针仍是野指针——这是链表题最常见的错误。

*有序插入时维护 tail 指针*：

```c
s->next    = cur;
prev->next = s;
if (cur == NULL) p->tail = s;   /* 插在表尾，必须同步 tail */
```

**③ 调试过程中发现并修正的问题**

| 序号 | 问题现象 | 原因 | 修正 |
| :--: | -------- | ---- | ---- |
| 1 | `A*B` 结果只有对角线项 | 双重循环写成了单层循环，`t1`、`t2` 同时后移 | 改为对 A 每项遍历 B 全部项 |
| 2 | `A−B` 与 `A+B` 结果相同 | B 的剩余项未取负 | 引入 `signB` 参数统一处理 |
| 3 | 求导后出现 `x^-1` 项 | 常数项未跳过 | `if (expn == 0) continue;` |
| 4 | 菜单输入被"跳过"一次 | `scanf("%d")` 后遗留换行符 | 全部改用 `fgets` 读整行 |
| 5 | 打印为 `3.000000x^2` | 直接用 `%f` | 改用 `%.10g`，并省略系数 1 |
| 6 | 合并后残留系数为 0 的结点 | 只做了加法未做删除 | 相加后判零并删除结点、回退 `len` |

## 四、算法复杂度汇总

| 操作 | 时间复杂度 | 空间复杂度 | 说明 |
| ---- | ---------- | ---------- | ---- |
| 建立多项式（n 项） | O(n²) | O(n) | 逐项有序插入；若输入已降序可优化到 O(n) |
| 输出 | O(n) | O(1) | 一次遍历 |
| 相加 / 相减 | O(m+n) | O(m+n) | 有序归并 |
| 相乘 | O(m·(n+\|R\|)) | O(\|R\|) | 逐项相乘 + 有序累加 |
| 求导 | O(n²) | O(n) | 每项插入 O(n) |
| 求值 | O(n·log e) | O(1) | 快速幂 |
| 高斯-约当消元 | O(m·n²) | O(mn) | 列主元 |

> 建立与求导的 O(n²) 可以优化：因为输入本身有序（建立时逐项读入通常是降序），
> 可直接尾插；求导后指数依然递减，同样可尾插。当前实现为通用性保留了
> `InsertTerm`，在 n < 1000 时差异可忽略。

## 五、思考题

> **线性表的存储可以采用顺序存储结构和链式存储结构两种方式，
> 在解决问题过程中二者有何不同，如何选择？**

### 5.1 两种存储结构的本质差异

顺序存储用一段**连续**的内存单元依次存放元素，逻辑相邻即物理相邻，
位置关系由下标隐式表示；链式存储用一组**任意**的存储单元，逻辑关系由
指针显式表示，每个结点除数据外还要存放指针。

### 5.2 具体比较

| 比较维度 | 顺序存储（数组） | 链式存储（单链表） |
| -------- | ---------------- | ------------------ |
| 存储密度 | 1（只存数据） | < 1（每个结点多一个指针域，64 位下 8 字节） |
| 随机访问 | **O(1)**，`a[i]` 直接定位 | **O(n)**，必须从头遍历 |
| 按值查找 | O(n)（可用二分则 O(log n)） | O(n) |
| 插入 / 删除 | **O(n)**，平均移动一半元素 | **O(1)**（已知前驱指针时），仅改指针 |
| 空间分配 | 静态，需**预先估计**容量；估小了溢出，估大了浪费 | 动态，**按需申请**，有多少项用多少空间 |
| 扩容 | 需重新申请 + 整体复制（均摊 O(1)，但有峰值开销） | 天然支持，无扩容概念 |
| 内存碎片 | 要求连续大块内存，易产生外部碎片 | 任意小块均可利用，无外部碎片（但有指针开销） |
| 缓存友好性 | **好**，连续访问命中率高，常数因子小 | 差，指针跳转易 cache miss |
| 实现复杂度 | 简单，下标运算直观 | 复杂，易出现野指针、内存泄漏、断链 |
| 适用规模 | 规模可预估、相对稳定 | 规模未知或剧烈变化 |

### 5.3 结合本实验的具体分析

一元稀疏多项式的关键特征是**项数 m 远小于最高次数 maxexp**。

以 `A(x) = 9x⁸ + 3x + 7` 为例：

- **顺序存储（下标即指数）**：需要 9 个单元存 `[7, 3, 0, 0, 0, 0, 0, 0, 9]`，
  有效数据只有 3 个，**空间利用率 33%**；若指数是 100000，则需要 100001 个
  单元而实际只有 2 项，利用率趋近于 0，完全不可行。
- **链式存储**：只需 3 个结点，空间与项数成正比，与指数大小无关。

再比较运算：

| 运算 | 顺序存储（下标即指数） | 链式存储（有序链表） |
| ---- | ---------------------- | -------------------- |
| 相加 | O(maxexp)，需逐下标对齐，稀疏时大量空转 | **O(m+n)**，只处理非零项 |
| 相乘 | O(maxexp²)，卷积 | O(m·(n+\|R\|)) |
| 输出 | 需扫描全部 maxexp 个位置 | O(m)，只遍历非零项 |
| 求值 | O(maxexp)，可用秦九韶 | O(m·log e) |

因此本实验**必须**选择链式存储：它不是"更好"，而是稀疏场景下唯一合理的选择。

但反过来，如果多项式是**稠密**的（例如 `(x+1)^20` 展开后有 21 项，指数 0~20 连续），
顺序存储反而更优：加法只需 O(n) 的一次扫描且常数极小、支持随机访问、
不需要为每个结点额外付出指针开销、缓存命中率高。此时链表的指针开销
（21×8 = 168 字节）甚至超过了数据本身。

### 5.4 选择准则

实际工程中可按以下顺序判断：

1. **规模能否预估？**
   能且稳定 → 顺序存储；不能或变化剧烈 → 链式存储。
2. **操作以"查"为主还是以"改"为主？**
   频繁随机访问 / 按下标读写 → 顺序；频繁在中间插入删除 → 链式。
3. **数据是否稀疏？**
   稀疏（大量位置为空）→ 链式；稠密连续 → 顺序。
4. **对空间还是时间更敏感？**
   内存紧张、元素本身很小 → 顺序（省指针）；追求插入删除的确定性 → 链式。
5. **是否有实时性要求？**
   顺序存储的插入可能触发整体复制，最坏情况有抖动；链式单次操作时间稳定。
6. **开发成本**：顺序存储代码简单、不易出错；链表需要谨慎处理边界与内存。

### 5.5 折中方案

实际系统很少非此即彼，常见的折中结构：

- **动态数组**（C++ `vector`、Java `ArrayList`）：顺序存储 + 自动扩容，
  兼顾随机访问与规模弹性，扩容均摊 O(1)；
- **静态链表**：在数组里用"游标"代替指针，兼得连续内存与免移动插入，
  适合不支持指针的语言或固定内存池场景；
- **块状链表**：每块内顺序、块间链式，兼顾缓存友好与插入效率；
- **哈希表**（以指数为键）：多项式合并可做到期望 O(1) 定位同类项，
  适合项数极多且指数范围大的场合，但失去有序性，输出时仍需排序。

### 5.6 结论

顺序存储与链式存储没有绝对优劣，本质是**时间、空间、实现复杂度三者的权衡**：
顺序存储用"连续空间"换来了随机访问与缓存友好，代价是插入删除的移动开销和
容量预估的风险；链式存储用"指针空间"换来了动态伸缩与 O(1) 插入删除，
代价是失去随机访问并增加实现难度。

就本实验而言，一元稀疏多项式的稀疏性决定了链式存储是正确选择；
而一旦问题变为稠密多项式或需要频繁按下标访问，就应当换回顺序存储。
**"根据数据的稀疏程度与操作类型选择存储结构"，正是本次实验最核心的收获。**

## 七、实验总结

### 7.1 从接到任务到解决问题的过程

1. **读题与建模**：先把"多项式"抽象成"有序对 (系数, 指数) 的集合"，
   再确定"指数递减、无零项"这一不变式——这一步决定了后面所有算法的写法。
2. **选存储结构**：比较数组与链表在稀疏场景下的空间开销，选定带头结点的单链表。
3. **设计接口**：先写头文件，把"能做什么"固定下来，再写实现。
4. **分模块编码**：数据结构 → 运算 → 界面，每完成一个模块立即用小程序验证。
5. **调试与排错**：乘法漏交叉项、减法漏取负、求导漏判常数项等问题，
   都是通过"用已知答案的小用例"逐个定位的。
6. **测试与优化**：补充边界用例（零多项式、系数抵消、非法输入），
   用 ASan 与 leaks 检查内存，最后整理文档。

### 7.2 收获与体会

- **不变式思维**：一旦确立"链表始终按指数递减且无零项"，加法只需归并、
  乘法只需有序插入，很多边界情况自然消失。数据结构的设计比算法的技巧更重要。
- **头结点的价值**：去掉头结点后，插入/删除首项要写两套代码；加上头结点后
  只需一套。这是"用一点空间换代码简洁与正确性"的典型例子。
- **指针的指针**：`MakeNode(Link *p, ...)` 必须用二级指针，因为要修改的是
  调用者的指针变量本身，这一点在写链表时最容易混淆。
- **浮点比较**：`coef == 0` 是错误写法，应使用 `fabs(coef) < 1e-12`。
  同时输出用 `%.10g` 而不是 `%f`，既避免 `3.200000` 的冗余，也避免
  `28.799999` 这类误差外露。
- **工程习惯**：接口与实现分离、统一状态码、编译零警告、退出前释放内存、
  自带自检用例——这些"看不见"的工作，恰恰是程序能否被验收的关键。

### 7.3 可改进方向

1. 建立与求导可改为尾插，把 O(n²) 降到 O(n)；
2. 乘法可用哈希表按指数聚合，把 O(m·n·k) 降到期望 O(mn)；
3. 系数可用分数（有理数）表示，彻底消除浮点误差；
4. 方程组模块可增加列主元 LU 分解，支持更大规模与稀疏矩阵；
5. 界面可移植到 ncurses，实现真正的全屏交互。
